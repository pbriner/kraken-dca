# Security Policy

## Security Features

This application has been designed with security as a primary concern and is ready for penetration testing.

### Architecture Security

1. **Minimal Attack Surface**
   - Zero external dependencies (uses only Python standard library)
   - No SQL database (eliminates SQL injection)
   - No shell command execution (eliminates command injection)
   - Direct HTTPS API communication only

2. **Input Validation**
   - All configuration values validated on startup
   - Trading pair format validation
   - Numeric range validation (deposit_day: 1-28)
   - Type checking on all inputs

3. **Secure API Communication**
   - HTTPS only (no HTTP fallback)
   - Proper HMAC-SHA512 signature generation
   - Nonce-based replay attack prevention
   - API keys never logged or exposed in error messages

4. **Container Security**
   - Runs as non-root user (UID 1000)
   - Minimal base image (python:3.11-slim)
   - All capabilities dropped (`cap_drop: ALL`)
   - No privilege escalation (`no-new-privileges:true`)
   - Limited file system access

5. **Data Protection**
   - API credentials (and the optional Telegram bot token) come exclusively from environment variables, loaded from a `.env` file that is never committed to git or baked into the Docker image
   - `config.json` and `transactions.json` are volume-mounted, not baked into the image; still protect with file permissions since `transactions.json` reveals trade history
   - Transaction data in JSON format (no sensitive data exposure)
   - No plaintext password storage

### Threat Model

#### Protected Against

✅ **SQL Injection**: No database used
✅ **Command Injection**: No shell execution
✅ **Path Traversal**: Validates and restricts file access
✅ **XSS**: No web interface
✅ **CSRF**: No web interface
✅ **API Key Exposure**: Never logged; credentials are read exclusively from `KRAKEN_API_KEY`/`KRAKEN_API_SECRET` environment variables (via a gitignored `.env`), not stored in `config.json`
✅ **Privilege Escalation**: Non-root container user
✅ **Replay Attacks**: Nonce-based API signatures
✅ **Man-in-the-Middle**: HTTPS only with certificate verification

#### Risks to Consider

⚠️ **`.env` File Access**: If an attacker gains file system access to the host, `.env` (API keys, Telegram bot token) is readable
- Mitigation: Use proper file permissions (600), consider Docker secrets or a vault for production
- `.env` is gitignored and never baked into the Docker image, but it is not encrypted at rest

⚠️ **Docker Host Compromise**: Container isolation protects against application exploits, but not host-level attacks
- Mitigation: Keep Docker host updated, use security scanning

⚠️ **API Key Permissions**: Over-permissioned API keys could allow unauthorized actions
- Mitigation: Use minimal permissions (Query Funds + Create Orders only)
- Never enable: Withdraw Funds permission

⚠️ **Rate Limiting**: Application respects time-based DCA, but doesn't explicitly rate limit API calls
- Mitigation: Kraken enforces server-side rate limits

⚠️ **Telegram Bot Exposure** (if enabled): The bot token is a bearer credential — anyone who has it can control the bot, and the bot only distinguishes users by `telegram_chat_id`
- Mitigation: Treat `TELEGRAM_BOT_TOKEN` like an API secret — env var only, never in `config.json` or logs
- Mitigation: Until `telegram_chat_id` is set, the bot replies to any sender with their chat ID only — no portfolio data, no buy capability
- Mitigation: Once `telegram_chat_id` is set, every message and callback query is checked against it; non-matching chats get "Unauthorized"
- Mitigation: `/buy` requires an explicit inline-button confirmation (single message, no button double-fire) before placing a real order, and still respects `max_price`/`max_monthly_amount`
- Note: Telegram integration is outbound-only long polling — it opens no inbound port and adds no listening service to the container
- Note: Every executed buy (scheduled, dip, or manual) now sends an automatic Telegram notification — no new inbound surface, just an additional outbound message per trade

⚠️ **Third-Party Chart Rendering** (`/chart` command, if used): chart images are generated by sending a Chart.js config (trading pair, dates, aggregated daily prices and BTC-held figures — no credentials) as a URL to the public [QuickChart.io](https://quickchart.io) service, which Telegram's servers then fetch
- This is the one deliberate exception to the "Kraken + Telegram only" outbound network model — no local charting library is used, to keep the zero-dependency design
- No API keys, transaction IDs, or account identifiers are sent — only price/date/amount aggregates already visible in `/status`
- Mitigation: if sending trading data to a third party is unacceptable for your use case, avoid the `/chart` command — no other feature depends on it

## Penetration Testing Guidelines

### Recommended Testing Scenarios

1. **Input Validation Testing**
   ```bash
   # Test invalid config values
   - deposit_day: 0, 29, -1, "invalid"
   - crypto_amount: 0, -0.01, "not_a_number"
   - trading_pair: "../../../etc/passwd", "<script>", "'; DROP TABLE--"
   - api_key/api_secret: null, empty string, very long strings
   ```

2. **File System Access Testing**
   ```bash
   # Attempt path traversal
   - Modify config paths to ../../../etc/passwd
   - Attempt to write outside /app directory
   - Test symbolic link following
   ```

3. **API Security Testing**
   ```bash
   # Test API interaction
   - Invalid API credentials
   - Expired/revoked API keys
   - Malformed API requests
   - Replay attack attempts
   ```

4. **Container Escape Testing**
   ```bash
   # Attempt privilege escalation
   docker exec -it kraken-dca /bin/bash
   # Try to access host resources
   # Attempt capability-based exploits
   ```

5. **Denial of Service Testing**
   ```bash
   # Resource exhaustion
   - Very large transaction.json file
   - Rapid API calls (should be prevented by DCA timing)
   - Memory exhaustion attempts
   ```

### Known Limitations

1. **`.env` File Security**: Credentials stored in plaintext on the host filesystem (not in `config.json`, but still plaintext at rest)
   - For production, consider using Docker secrets or HashiCorp Vault

2. **No Authentication on the Core App**: The bot itself assumes a trusted host environment. The Telegram integration adds chat-ID gating for its own commands, but that only authorizes Telegram interactions, not the underlying process/API access
   - For multi-user scenarios, add an authentication layer

3. **No Rate Limiting**: Relies on Kraken's (and Telegram's) server-side limits
   - For aggressive strategies, implement client-side rate limiting

4. **Transaction Log Growth**: transactions.json grows indefinitely
   - For long-term use, implement log rotation

### Security Best Practices

1. **File Permissions**
   ```bash
   chmod 600 config.json
   chmod 600 transactions.json
   chmod 600 .env
   ```

2. **Docker Secrets** (Production)
   ```yaml
   services:
     kraken-dca:
       secrets:
         - kraken_api_key
         - kraken_api_secret
   
   secrets:
     kraken_api_key:
       external: true
     kraken_api_secret:
       external: true
   ```

3. **Network Isolation**
   ```yaml
   services:
     kraken-dca:
       networks:
         - isolated
   
   networks:
     isolated:
       internal: true  # No internet access except specified
   ```

4. **Regular Updates**
   ```bash
   # Update base image
   docker pull python:3.11-slim
   docker compose build --no-cache
   ```

## Security Checklist for Deployment

- [ ] API key has minimal permissions (no withdrawal)
- [ ] `.env`, `config.json`, and `transactions.json` have restricted permissions (600)
- [ ] Kraken credentials are set via `KRAKEN_API_KEY`/`KRAKEN_API_SECRET`, not in `config.json`
- [ ] If Telegram is enabled: `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` are both set via env vars, not `config.json` (bot won't gate on an empty chat ID)
- [ ] Docker host is updated and patched
- [ ] Container resource limits are set
- [ ] Logs are monitored for suspicious activity
- [ ] Transaction history is backed up regularly
- [ ] API keys (and Telegram bot token, if used) are rotated periodically
- [ ] Test with small amounts before production use
